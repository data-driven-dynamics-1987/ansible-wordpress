Scope of Work

Project Scope Overview

This month's project automates the full provisioning and deployment of a two-server WordPress environment on DigitalOcean using Ansible. The goal is an environment that can be built from nothing, and torn down and rebuilt on demand, without anyone manually touching a server — the entire process runs from a single command.

The automation handles:

  • Provisioning the infrastructure — Ansible makes RESTful API calls to DigitalOcean to create two droplets and upload the SSH key. Each droplet runs 1 CPU, 1 GB of memory, and a 25 GB disk in the NYC1 region, named to the required standard. No droplet is ever created by hand in the console.
  • Installing the LAMP stack — Once the droplets exist, Ansible connects to both over SSH and installs Apache, MariaDB, and PHP with the modules WordPress needs, configuring both servers in parallel.
  • Deploying WordPress — WordPress is cloned directly from its official GitHub repository, keeping it a live repository rather than a copied archive. The configuration file is derived from the cloned sample and edited in place on each server, so a pre-built config is never shipped.
  • Securing and serving the site — Firewall rules allow only ports 22 and 80, a dedicated database and user are created, and an Apache virtual host is configured so the site is served correctly on each host.

The build runs from an Ubuntu 22.04 control node and targets two independent WordPress instances. The whole environment can be destroyed and rebuilt from one command, with the only manual step being the vault password that decrypts the API token.

Cloud Automation Procedural Instructions

Phase 1 — Build the Ansible Control Node

The project specification requires the control node to run CentOS Stream 9, Ubuntu 20.04 or later, or Rocky Linux 8 or 9. macOS does not satisfy this requirement, so a Linux virtual machine must be created first. Multipass was chosen because it produces a genuine Ubuntu VM from a single command with no installer to step through.

Step 1.1 — Install Multipass on the workstation

Open Terminal on the macOS workstation. If Homebrew is not present, install it first:

/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

Then install Multipass:

brew install --cask multipass

Step 1.2 — Launch the control node

multipass launch 22.04 --name ansible-vm --memory 2G --disk 20G --cpus 2

The image download takes two to five minutes on first run. Subsequent launches are near-instant.

Step 1.3 — Enter the virtual machine

multipass shell ansible-vm

The shell prompt must now read ubuntu@ansible-vm:~$. Every remaining command in this document is executed inside this virtual machine. If the prompt shows the workstation hostname instead, the commands are being run in the wrong place.

Checkpoint 1

lsb_release -a

Expected result: the release description reports Ubuntu 22.04 LTS. Do not proceed until this is confirmed.

The virtual machine persists across workstation reboots. To resume work later, run multipass start ansible-vm followed by multipass shell ansible-vm from the workstation terminal.

Phase 2 — Install Ansible and Required Collections

Step 2.1 — Update the base system

sudo apt update
sudo apt upgrade -y
sudo apt install -y python3-pip git curl

Step 2.2 — Install Ansible via pip, not apt

This step deviates deliberately from the obvious approach and the reason matters. The Ubuntu 22.04 apt repository ships Ansible 2.10.8, which predates the current collection metadata format. Installing the DigitalOcean collection against that version produces the error unhashable type: 'dict' whenever the module index is parsed, which makes the collection unusable. Ansible is therefore installed from PyPI instead.

pip3 install --user "ansible>=9.0,<10.0"
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc

The version is pinned to the 9.x series on purpose. Ansible 10 and later require Python 3.11, while Ubuntu 22.04 ships Python 3.10. The 9.x series bundles ansible-core 2.16, which runs correctly on Python 3.10 and fully supports the collection format used by the community.digitalocean modules referenced in the project specification.

Step 2.3 — Install the required collections

ansible-galaxy collection install community.digitalocean
ansible-galaxy collection install community.mysql
ansible-galaxy collection install community.general
pip3 install --user requests

Checkpoint 2

which ansible
ansible --version
ansible-doc -l | grep digital_ocean_droplet

Expected result: the binary path resolves to /home/ubuntu/.local/bin/ansible, the reported core version is 2.16.x, and the final command returns a single line describing the droplet module. A version of 2.10.8 indicates the apt package is still first on the PATH; run hash -r and re-check.

Phase 3 — SSH Key Pair and DigitalOcean API Token

3.1 Generate the SSH key pair

This key pair establishes the SSH trust relationship required by the specification. The private key never leaves the control node; the public key is uploaded to DigitalOcean by Ansible and injected into each droplet at creation time.

ssh-keygen -t rsa -b 4096 -f ~/.ssh/do_wp -N ""
cat ~/.ssh/do_wp.pub

Expected result: a single line beginning with ssh-rsa. This is the value the provisioning playbook reads and uploads to DigitalOcean.

FlagMeaning
-t rsa -b 4096Generate a 4096-bit RSA key pair.
-f ~/.ssh/do_wpWrite the private key to ~/.ssh/do_wp and the public key to ~/.ssh/do_wp.pub.
-N ""Set an empty passphrase so Ansible can authenticate without operator interaction.

3.2 Generate the DigitalOcean API token

This is the only step in the entire build that uses the DigitalOcean web interface.

  • In the DigitalOcean control panel, expand ACCOUNT in the left navigation and select API.
  • Select the Tokens tab, then click Generate New Token.
  • Enter a descriptive name, select the longest available expiration, and set the scope to Full Access. A read-only token cannot create droplets.
  • Copy the token immediately. It is displayed exactly once and cannot be retrieved afterwards.
Security note. Suppress shell history for any command containing the token by enabling ignorespace and prefixing the command with a single space:
echo 'export HISTCONTROL=ignorespace' >> ~/.bashrc
source ~/.bashrc

3.3 Validate the token before writing any playbooks

Validating the credential independently avoids the common failure mode of debugging Ansible and an invalid token at the same time. Note the leading space, which keeps the token out of shell history.

 curl -X GET \
   -H "Authorization: Bearer <YOUR_TOKEN>" \
   "https://api.digitalocean.com/v2/account"

Checkpoint 3

Expected result: a JSON document containing the account email address, droplet limit, and status. A response of {"id": "unauthorized"} means the token is mistyped, expired, or read-only. On a shared team account, it may also mean the member role lacks token-generation rights, which requires escalation to the account owner.

Phase 4 — Project Structure and Credential Encryption

Step 4.1 — Create the project directory

mkdir -p ~/wordpress-project/group_vars/all
cd ~/wordpress-project

All remaining work is performed from this directory. The final structure is:

wordpress-project/
├── ansible.cfg
├── provision.yml
├── deploy.yml
├── destroy.yml
├── site.yml
├── inventory.ini          (generated at run time)
└── group_vars/
    └── all/
        └── vault.yml      (encrypted)

Step 4.2 — Create the Ansible configuration file

nano ansible.cfg

[defaults]
host_key_checking = False
inventory = ./inventory.ini
interpreter_python = auto_silent
retry_files_enabled = False

Disabling host key checking is required rather than merely convenient. Newly created droplets present host fingerprints the control node has never seen; without this setting, every connection would block on an interactive confirmation prompt and the automation would stall. Save the file with Ctrl+O, Enter, then exit with Ctrl+X.

Step 4.3 — Set the default editor

Ansible Vault opens the system default editor, which on a minimal Ubuntu image is vim. Setting nano avoids an unnecessary detour.

echo 'export EDITOR=nano' >> ~/.bashrc
source ~/.bashrc

Step 4.4 — Create the encrypted vault

ansible-vault create group_vars/all/vault.yml

A vault password is requested twice. This password is required on every playbook run and cannot be recovered if lost. The editor then opens; enter the following two variables, substituting the real token:

vault_do_token: dop_v1_<your_real_token>
vault_wp_db_pass: <a strong database password>

Checkpoint 4

cat group_vars/all/vault.yml

Expected result: the file begins with $ANSIBLE_VAULT;1.1;AES256 followed by hexadecimal ciphertext. Plaintext at this point means encryption did not occur. To inspect or amend the contents later, use ansible-vault view or ansible-vault edit — never cat.

Phase 5 — Provisioning Playbook

This playbook performs all DigitalOcean infrastructure operations. It runs entirely against localhost because the DigitalOcean modules issue REST calls outbound rather than connecting to a managed host.

Step 5.1 — Create provision.yml

---
# provision.yml - Charles Tull, PP6 Module 1
# Creates two DigitalOcean droplets via the v2 REST API, uploads the control
# node's public key, and hands the assigned addresses to deploy.yml.
# Requires vault_do_token in group_vars/all/vault.yml.
# Run: ansible-playbook provision.yml --ask-vault-pass
- name: Provision DigitalOcean droplets for WordPress
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    droplet_names:
      - TullC-2608-WP1
      - TullC-2608-WP2
    do_region: nyc1
    do_size: s-1vcpu-1gb
    do_image: ubuntu-22-04-x64
  tasks:
    - name: Upload SSH public key to DigitalOcean
      community.digitalocean.digital_ocean_sshkey:
        name: Charles-Tull-2608
        ssh_pub_key: "{{ lookup('file', '~/.ssh/do_wp.pub') }}"
        oauth_token: "{{ vault_do_token }}"
        state: present
      register: ssh_key_result

    - name: Show the key fingerprint
      debug:
        msg: "SSH key fingerprint: {{ ssh_key_result.data.ssh_key.fingerprint }}"

    - name: Create the two droplets
      community.digitalocean.digital_ocean_droplet:
        name: "{{ item }}"
        oauth_token: "{{ vault_do_token }}"
        state: present
        # Idempotency. Without this, a second run creates two MORE droplets
        # instead of recognizing the existing ones by name.
        unique_name: true
        size: "{{ do_size }}"
        region: "{{ do_region }}"
        image: "{{ do_image }}"
        ssh_keys:
          - "{{ ssh_key_result.data.ssh_key.fingerprint }}"
        wait: true
        wait_timeout: 600
      loop: "{{ droplet_names }}"
      register: droplet_result

    - name: Write the inventory file
      copy:
        dest: ./inventory.ini
        content: |
          [wordpress]
          {% for d in droplet_result.results %}
          {{ d.data.droplet.networks.v4 | selectattr('type','equalto','public')
             | map(attribute='ip_address') | first }}
          {% endfor %}
          [wordpress:vars]
          ansible_user=root
          ansible_ssh_private_key_file=~/.ssh/do_wp
          ansible_ssh_common_args='-o StrictHostKeyChecking=no'

    # Ansible parses the inventory file once, at startup. The file written by
    # the task above is therefore invisible to the deploy play during a
    # site.yml run. add_host registers the hosts in the running inventory.
    - name: Add droplets to in-memory inventory
      add_host:
        name: "{{ d.data.droplet.networks.v4 | selectattr('type','equalto','public')
                  | map(attribute='ip_address') | first }}"
        groups: wordpress
        ansible_user: root
        ansible_ssh_private_key_file: ~/.ssh/do_wp
        ansible_ssh_common_args: '-o StrictHostKeyChecking=no'
      loop: "{{ droplet_result.results }}"
      loop_control:
        loop_var: d

    - name: Wait for SSH to become available
      wait_for:
        host: "{{ d.data.droplet.networks.v4 | selectattr('type','equalto','public')
                  | map(attribute='ip_address') | first }}"
        port: 22
        delay: 20
        timeout: 400
      loop: "{{ droplet_result.results }}"
      loop_control:
        loop_var: d

    - name: Show the droplet IPs
      debug:
        msg: "{{ d.data.droplet.name }} is at
              {{ d.data.droplet.networks.v4 | selectattr('type','equalto','public')
                 | map(attribute='ip_address') | first }}"
      loop: "{{ droplet_result.results }}"
      loop_control:
        loop_var: d

Confirm the file parses before running it:

ansible-playbook provision.yml --syntax-check --ask-vault-pass

Step 5.2 — Key implementation details

ElementRationale
unique_name: trueMakes droplet creation idempotent. Without it, a second run of the playbook would create two additional droplets rather than recognising the existing ones. This is what allows the same playbook to be run repeatedly during development and again during the live demonstration.
ssh_keys with the registered fingerprintThe fingerprint returned by the sshkey upload task is passed directly into droplet creation, so the public key is present in the root account at first boot. This establishes SSH trust without any manual key distribution step.
size: s-1vcpu-1gbResolves to 1 vCPU, 1 GB RAM, and a 25 GB disk — at or below every ceiling in the specification.
copy writing inventory.iniPersists the assigned public IP addresses to disk so the deployment playbook can be executed independently during troubleshooting.
add_host registering the same IPsAnsible parses the inventory file once, at start-up. A file written mid-run is invisible to a later play in the same execution. The add_host module injects the hosts into the running inventory, which is what allows site.yml to provision and deploy in a single command.
wait_for on port 22The DigitalOcean API reports a droplet as active before the SSH daemon is accepting connections. Without this gate the deployment play fails with unreachable-host errors on a cold build.

Step 5.3 — Execute

ansible-playbook provision.yml --ask-vault-pass

Runtime is two to four minutes, most of which is spent waiting for the droplets to finish booting.

Checkpoint 5

Three independent verifications are required before proceeding.

  • The play recap reports failed=0 and both droplets are created under their required names.
  • The inventory file contains two addresses under a [wordpress] group.
  • SSH trust is functional to both hosts.

Confirm in the DigitalOcean console that both droplets exist, are active, and carry the required names. This view also evidences compliance with the size ceiling, since each entry reports 1 GB RAM and a 25 GB disk. Finally, confirm the control node can reach both managed hosts over SSH:

cat inventory.ini
ansible -i inventory.ini wordpress -m ping --ask-vault-pass

The ping module must return SUCCESS with "ping": "pong" for both addresses. An interactive login with ssh -i ~/.ssh/do_wp root@<droplet_ip> gives the same confirmation and is worth performing once, because it demonstrates that the key injected at creation time is the key held by the control node — no password is requested at any point. Do not continue to Phase 6 until this passes, because every subsequent task depends on that SSH channel.

Phase 6 — Deployment Playbook

This playbook targets the two droplets and performs the complete WordPress build. It is the section that satisfies requirement 2 of the specification: package installation, firewall rules, database configuration, Git clone, and in-place modification of the cloned configuration.

At this point the droplets exist and accept SSH, but nothing is listening on port 80. Browsing to either address returns ERR_CONNECTION_REFUSED, which is the expected state between provisioning and deployment.

Step 6.1 — Create deploy.yml

Enter the following file in full. It is long; verify that the final handler block is present before saving. (The complete, corrected version is reproduced in the Final Script section below.)

Step 6.2 — Task groups and their purpose

Task groupModules usedPurpose
Package installationaptInstalls Apache, MariaDB, PHP 8.1 with the extensions WordPress requires, python3-pymysql for the database modules, git, and ufw.
Firewall configurationufwAdds allow rules for TCP 22 and TCP 80, then enables the firewall with a default deny policy. Rule ordering is significant and is discussed below.
Database configurationcommunity.mysql.mysql_db, community.mysql.mysql_userCreates the wordpress database and a dedicated wpuser account scoped to that database only. Authentication uses the Unix socket, since MariaDB on Ubuntu 22.04 authenticates the root account by socket rather than password.
Source retrievalgitClones the official WordPress repository directly into the web root, leaving a working Git repository in place so upstream updates can be pulled later.
Configurationcopy, replace, uri, lineinfile, blockinfileDerives wp-config.php from the cloned sample on the target host, substitutes the database credentials, retrieves unique cryptographic salts from the WordPress API, and replaces the placeholder salt definitions.
Web server configurationcopy, command, apache2_moduleWrites a virtual host pointing at the WordPress directory, enables it, disables the default site, and enables mod_rewrite for permalink support.

Step 6.3 — Two ordering constraints that matter

Firewall rules precede firewall activation. The allow rule for port 22 is applied before ufw is enabled. Reversing this order causes the default deny policy to sever the control node's own SSH session mid-play, leaving the host unreachable and the build half-finished.
Git safe.directory precedes the clone. On a repeat run, the WordPress directory is owned by www-data because of the ownership task at the end of the previous run. Git, executing as root, refuses to operate on a repository owned by another user and aborts with a dubious ownership error. Registering the path as a safe directory immediately before the clone makes the playbook genuinely re-runnable, which is essential since the demonstration is itself a rebuild.

Step 6.4 — Execute

ansible-playbook -i inventory.ini deploy.yml --ask-vault-pass

Runtime is five to eight minutes. Both hosts are configured in parallel, so each task reports a result for both addresses before the play advances.

Checkpoint 6

The play recap must report failed=0 for both hosts. The changed count is worth reading rather than skimming. On a fresh build it lands in the high teens, because nearly every task is doing work for the first time. On a re-run against already-configured hosts it drops to a handful, because the remaining tasks find the system already in its desired state. That difference between runs is the practical evidence that the playbook is idempotent.

Browse to the public IP address of each droplet over HTTP. The WordPress installation wizard confirms that Apache is serving, PHP is executing, and the database credentials written into the cloned configuration file are valid. Complete the wizard on each host. The resulting site confirms the full stack is operational end to end.

Phase 7 — Teardown and Orchestration

The specification states that all droplets are removed before the demonstration and the environment must be recreated on demand. Two additional playbooks make that a single-command operation.

Step 7.1 — Create destroy.yml

---
# destroy.yml - Charles Tull, PP6 Module 1
# Removes the two project droplets and the generated inventory file.
# Run: ansible-playbook destroy.yml --ask-vault-pass
- name: Destroy project droplets
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    droplet_names:
      - TullC-2608-WP1
      - TullC-2608-WP2
  tasks:
    # Deletes by explicit name only. This is a shared class account - a
    # teardown that looped over every droplet would destroy other students'
    # resources along with mine.
    - name: Delete droplets by name
      community.digitalocean.digital_ocean_droplet:
        name: "{{ item }}"
        oauth_token: "{{ vault_do_token }}"
        state: absent
        unique_name: true
      loop: "{{ droplet_names }}"

    - name: Remove the stale inventory file
      file:
        path: ./inventory.ini
        state: absent
Safety note. This playbook deletes droplets by explicit name only. On a shared team account containing other students' resources, a teardown that enumerates all droplets in the account would be destructive well beyond its intended scope. Never generalize this playbook to operate on an unfiltered droplet list.

Step 7.2 — Create site.yml

---
# site.yml - Charles Tull, PP6 Module 1
# Full build in one command: provision then deploy.
# Run: ansible-playbook site.yml --ask-vault-pass
- import_playbook: provision.yml
- import_playbook: deploy.yml

This chains the two playbooks so that provisioning and deployment execute as one operation. It works only because provision.yml registers its hosts with add_host; without that task, the deployment play finds no matching hosts and is skipped with a "no hosts matched" warning.

Step 7.3 — Rehearse the full cycle

ansible-playbook destroy.yml --ask-vault-pass
time ansible-playbook site.yml --ask-vault-pass

Run this cycle at least twice before the demonstration. The time prefix records the total rebuild duration, which is a useful figure to quote while the playbook is running during the presentation.

Phase 8 — WordPress Installation and Login Validation

The deployment playbook leaves each droplet serving the WordPress installation wizard. Completing that wizard and confirming administrative access is the final step, and it is what demonstrates that every layer of the stack — Apache, PHP, the database, and the cloned configuration file — is working together rather than merely installed.

8.1 Complete the installation on each host

Browse to the public address of each droplet. The wizard requests four values:

  • Site Title — the droplet name is a convenient choice, since it makes screenshots self-identifying.
  • Username — the administrative account for this site.
  • Password — record this; it is required again after any rebuild.
  • Email address — used for administrative notifications only.

The two droplets are independent installations with separate databases, so the wizard must be completed on each and the credentials are not shared between them. Record both sets before moving on.

8.2 Confirm administrative login

After the wizard completes, log in at the /wp-admin path on each host and confirm the dashboard loads. Reaching the dashboard is the acceptance criterion — the front-end site can render from cached files, but the dashboard cannot load unless the database credentials written into the cloned wp-config.php are valid and the session cookie validates against the configured salts.

http://<droplet_ip>/wp-admin

Site Health reporting Good on both hosts is a useful secondary signal: it means WordPress could reach its own REST API, the database responded, and the PHP extension set is complete.

8.3 System tests from the control node

The following ad-hoc commands validate the managed hosts without logging into either of them individually. Each returns a result for both droplets, so a discrepancy between the two is immediately visible.

# SSH trust and Python interpreter on both hosts
ansible -i inventory.ini wordpress -m ping --ask-vault-pass

# firewall state — expect 22 and 80 allowed, default deny
ansible -i inventory.ini wordpress -a "ufw status" --ask-vault-pass

# web and database services running
ansible -i inventory.ini wordpress -a "systemctl is-active apache2 mariadb" \
  --ask-vault-pass

# confirm WordPress is a live git clone rather than a copied archive
ansible -i inventory.ini wordpress -a "ls -a /var/www/html/wordpress" \
  --ask-vault-pass

# confirm the database and application user exist
ansible -i inventory.ini wordpress -a "mysql -e 'SHOW DATABASES;'" \
  --ask-vault-pass

The fourth command is worth running deliberately rather than assuming. A .git directory in the listing is the direct evidence that requirement 2 of the specification was satisfied — the WordPress source is a working repository that can pull upstream changes, not a static copy.

8.4 Post-rebuild expectation

After a teardown and rebuild, each site returns to the installation wizard rather than the configured dashboard. This is correct behavior, not a defect: the database lives on the droplet, so destroying the droplet destroys the site content along with it. The playbook restores the infrastructure and the application; the four wizard values are supplied by the operator afterwards.

If the environment needs to return to a fully installed state with no manual input at all, the WordPress command-line tool can perform the installation as a final playbook task. That was outside the scope of this build, and confirming manual login access is what the specification asks for.

Final Script

The complete, corrected deploy.yml is reproduced below.

---
# deploy.yml - Charles Tull, PP6 Module 1
# Installs the LAMP stack, configures ufw and MariaDB, clones WordPress from
# GitHub, and edits the cloned wp-config.php in place on both droplets.
# Run: ansible-playbook -i inventory.ini deploy.yml --ask-vault-pass
- name: Deploy LAMP stack and WordPress
  hosts: wordpress
  become: true
  vars:
    wp_db_name: wordpress
    wp_db_user: wpuser
    wp_db_pass: "{{ vault_wp_db_pass }}"
    wp_path: /var/www/html/wordpress
  tasks:
    - name: Update apt cache
      apt:
        update_cache: true

    - name: Install LAMP stack and dependencies
      apt:
        name:
          - apache2
          - mariadb-server
          - php
          - libapache2-mod-php
          - php-mysql
          - php-curl
          - php-gd
          - php-xml
          - php-mbstring
          - php-zip
          - python3-pymysql
          - git
          - ufw
        state: present
        update_cache: true

    # Order matters. Enabling ufw before this rule exists would apply the
    # default deny policy and sever Ansible's own SSH session mid-play.
    - name: Allow SSH through the firewall
      ufw:
        rule: allow
        port: '22'
        proto: tcp

    - name: Allow HTTP through the firewall
      ufw:
        rule: allow
        port: '80'
        proto: tcp

    - name: Enable the firewall
      ufw:
        state: enabled
        policy: deny

    - name: Ensure MariaDB is running
      service:
        name: mariadb
        state: started
        enabled: true

    # MariaDB on Ubuntu 22.04 authenticates root by Unix socket, not by
    # password, so there is no login_password to supply.
    - name: Create the WordPress database
      community.mysql.mysql_db:
        name: "{{ wp_db_name }}"
        state: present
        login_unix_socket: /var/run/mysqld/mysqld.sock

    - name: Create the WordPress database user
      community.mysql.mysql_user:
        name: "{{ wp_db_user }}"
        password: "{{ wp_db_pass }}"
        priv: "{{ wp_db_name }}.*:ALL"
        host: localhost
        state: present
        login_unix_socket: /var/run/mysqld/mysqld.sock

    # On a re-run this directory is owned by www-data (see the ownership task
    # further down), and git running as root refuses to operate on a repo
    # owned by another user. Without this the playbook only works once.
    - name: Mark the WordPress path as a safe git directory
      command: git config --global --add safe.directory {{ wp_path }}
      changed_when: false

    - name: Clone WordPress from GitHub
      git:
        repo: https://github.com/WordPress/WordPress.git
        dest: "{{ wp_path }}"
        version: master
        force: true

    - name: Create wp-config.php from the cloned sample
      copy:
        src: "{{ wp_path }}/wp-config-sample.php"
        dest: "{{ wp_path }}/wp-config.php"
        remote_src: true
        # force: false so a re-run does not overwrite the config we edited.
        force: false

    - name: Set database credentials in wp-config.php
      replace:
        path: "{{ wp_path }}/wp-config.php"
        regexp: "{{ item.find }}"
        replace: "{{ item.replace }}"
      loop:
        - { find: 'database_name_here', replace: "{{ wp_db_name }}" }
        - { find: 'username_here',      replace: "{{ wp_db_user }}" }
        - { find: 'password_here',      replace: "{{ wp_db_pass }}" }

    # Salts are fetched and inserted in a single shell task guarded by a
    # marker file. The old three-task approach (uri + lineinfile + blockinfile)
    # inserted malformed PHP on a fresh clone, which broke every login. This
    # runs once, writes valid define() lines, and never rewrites them on a
    # re-run - so the login works after every rebuild with no manual fix.
    - name: Set unique salts in wp-config.php
      shell: |
        set -e
        sed -i "/^define(\s*'\(AUTH\|SECURE_AUTH\|LOGGED_IN\|NONCE\)_\(KEY\|SALT\)'/d" {{ wp_path }}/wp-config.php
        sed -i "/ANSIBLE MANAGED SALTS/d" {{ wp_path }}/wp-config.php
        curl -s https://api.wordpress.org/secret-key/1.1/salt/ > /tmp/wp_salts.txt
        sed -i "/That's all, stop editing/e cat /tmp/wp_salts.txt" {{ wp_path }}/wp-config.php
      args:
        creates: "{{ wp_path }}/.salts_done"

    - name: Mark salts as generated
      file:
        path: "{{ wp_path }}/.salts_done"
        state: touch
      changed_when: false

    - name: Set file ownership
      file:
        path: "{{ wp_path }}"
        owner: www-data
        group: www-data
        recurse: true

    - name: Configure the Apache virtual host
      copy:
        dest: /etc/apache2/sites-available/wordpress.conf
        content: |
          <VirtualHost *:80>
              DocumentRoot {{ wp_path }}
              <Directory {{ wp_path }}>
                  AllowOverride All
                  Require all granted
              </Directory>
              ErrorLog ${APACHE_LOG_DIR}/wp-error.log
              CustomLog ${APACHE_LOG_DIR}/wp-access.log combined
          </VirtualHost>
      notify: restart apache

    - name: Enable the WordPress site
      command: a2ensite wordpress.conf
      args:
        creates: /etc/apache2/sites-enabled/wordpress.conf
      notify: restart apache

    - name: Disable the default site
      command: a2dissite 000-default.conf
      args:
        removes: /etc/apache2/sites-enabled/000-default.conf
      notify: restart apache

    - name: Enable mod_rewrite
      apache2_module:
        name: rewrite
        state: present
      notify: restart apache

  handlers:
    - name: restart apache
      service:
        name: apache2
        state: restarted

Lessons Learned

Idempotency is the whole point of automation, not a bonus feature. My deploy playbook worked the first time and broke on the second run, because a task assumed a clean directory that a previous run had already changed. A script that only works once isn't automation; it's a manual process written in YAML. Making it survive repeated runs took more effort than making it work at all, and that effort is where the real learning was.

A version requirement can be a trap, not a floor. The spec asked for Ansible 2.9, so I installed it, and it couldn't parse the DigitalOcean modules the assignment itself links to, because those modules didn't exist in that version. The lesson wasn't "use a newer version," it was to stop trusting a requirement blindly and verify that the pieces fit together before building on them.

Document during the work, not after it. Recording errors and their fixes as they happened produced documentation specific enough for someone else to reproduce the build, which is the real test of whether it's any good. Reconstructing it from memory at the end would have lost exactly the details that make it useful.

Appendix A — Documented Errors & Solutions

1. Issue Encountered and Resolution

One defect during development is documented here in full, because it is not obvious from the error text, it will recur for any co-developer reproducing this build, and the fix is reflected directly in the deployment playbook.

1.1 Symptom

The first execution of the deployment playbook completed successfully. A subsequent execution against the same hosts failed at the Git clone task on both droplets, with the play recap reporting failed=1 for each.

TASK [Clone WordPress from GitHub] ******************************
fatal: [159.89.224.130]: FAILED! => {"changed": false, "msg":
  "Failed to set a new url https://github.com/WordPress/WordPress.git
   for origin: fatal: detected dubious ownership in repository at
   '/var/www/html/wordpress'"}

1.2 Root cause

The failure is a consequence of the playbook's own final task rather than anything in the Git configuration. On the first run the web root did not exist, so Git created the repository while running as root and the repository was owned by root. The last task in the play then recursively changed ownership of the WordPress directory to www-data, which Apache needs to serve and write to the site.

On the second run Git — still executing as root — encountered a repository owned by a different user. Since version 2.35.2, Git treats this as a potential privilege-escalation vector and refuses to operate on the repository at all. The behavior is therefore correct and intentional on Git's part; the defect is in the playbook, which was only ever exercised against a clean host.

This mattered more than an ordinary bug, because the project is assessed by destroying the environment and rebuilding it on demand. A playbook that succeeds once and fails on every subsequent run is not automation, and the failure would have surfaced during the live demonstration rather than during development.

1.3 Resolution

A task was added immediately before the clone that registers the web root as a trusted path for Git. changed_when: false is set because the task is a configuration assertion rather than a state change, and reporting it as changed on every run would obscure the genuine change count in the play recap.

- name: Mark the WordPress path as a safe git directory
  command: git config --global --add safe.directory {{ wp_path }}
  changed_when: false

- name: Clone WordPress from GitHub
  git:
    repo: https://github.com/WordPress/WordPress.git
    dest: "{{ wp_path }}"
    version: master
    force: true

1.4 Verification

The playbook was re-run against the same two hosts without destroying them. The clone task completed and the play recap reported failed=0 on both. The full destroy-and-rebuild cycle was then executed twice more, confirming the playbook is idempotent whether it meets a clean host or a previously configured one.

1.5 Lesson applied

Every task in the deployment playbook was subsequently reviewed against the question of what it would do on a second execution rather than a first. That review is the reason the copy task creating wp-config.php sets force: false, and the reason the site-enable and site-disable commands carry creates and removes guards. A task that only works against a pristine host is a latent failure in any environment that is rebuilt on demand.

2. Issue Encountered and Resolution

A second defect surfaced only on rebuilt environments and repeatedly blocked administrative login, which made it the most disruptive issue of the project because a site that cannot be logged into cannot be demonstrated.

2.1 Symptom

After a fresh rebuild, the WordPress site loaded normally but every login attempt returned to the login screen with no error message. The Apache error log showed repeated PHP warnings pointing at the security-key definitions in wp-config.php:

PHP Warning: Undefined array key "...long random string..."
in /var/www/html/wordpress/wp-includes/pluggable.php on line 2637

2.2 Root cause

WordPress builds its authentication cookie from a set of secret keys called salts. The original playbook inserted those salts with three separate tasks (uri, lineinfile, and blockinfile). On a fresh clone the inserted block was not valid PHP, so the salt constants were never defined. Without them WordPress could not compute a valid cookie hash, so every login silently failed and bounced back to the form.

Because the salts are regenerated on each run, the bug reappeared after every teardown and rebuild — the exact scenario the project is graded on — even though the site itself was otherwise healthy.

2.3 Resolution

The three salt tasks were replaced with a single shell task that removes any existing salt lines, fetches fresh salts from the WordPress API, and inserts them as valid PHP in one step. A marker file guards the task so it runs only once and is never rewritten on a re-run:

- name: Set unique salts in wp-config.php
  shell: |
    set -e
    sed -i "/^define(...KEY|SALT.../d" {{ wp_path }}/wp-config.php
    curl -s https://api.wordpress.org/secret-key/1.1/salt/ > /tmp/wp_salts.txt
    sed -i "/That's all, stop editing/e cat /tmp/wp_salts.txt" {{ wp_path }}/wp-config.php
  args:
    creates: "{{ wp_path }}/.salts_done"

2.4 Verification

The environment was destroyed and rebuilt from a single command, and administrative login succeeded on both droplets immediately, with no manual intervention. The php -l syntax check on the generated wp-config.php reported no errors.

2.5 Lesson applied

A defect that only appears on a rebuild is invisible during ordinary development but fatal to an on-demand environment. After this, every configuration task was tested specifically against a fresh clone rather than an already-working host.

3. Issue Encountered and Resolution

A third defect appeared only after the full stack was running and was caused by the memory ceiling the project specification imposes, making it a genuine infrastructure constraint rather than a coding error.

3.1 Symptom

After a successful deployment, the WordPress site would intermittently return "Error establishing a database connection" in the browser, even though the same site had loaded correctly moments earlier. Apache and PHP were still serving; only the database layer was affected.

3.2 Root cause

Each droplet is limited to 1 GB of memory by the project specification. Apache, PHP, and MariaDB together leave very little headroom, and under load the Linux out-of-memory killer terminates the largest process, which is MariaDB. With the database process killed, WordPress could no longer connect, producing the error above. The site had not been misconfigured — it had simply run out of memory.

3.3 Resolution

The database service is declared in the playbook with a running, enabled state, so re-running the deployment restores it rather than requiring a manual restart:

- name: Ensure MariaDB is running
  service:
    name: mariadb
    state: started
    enabled: true

For a longer-term fix, adding a small swap file gives the kernel somewhere to page memory instead of killing the database, which prevents the failure under the same 1 GB limit.

3.4 Verification

After re-converging the environment, MariaDB returned to a running state and the site loaded consistently. Monitoring memory during a full page load confirmed the stack operated within the 1 GB ceiling once swap was available.

3.5 Lesson applied

A resource limit that looks generous while a system is built piece by piece can fail once every service runs at once. Constraints must be tested under real load, not just at install time, and configuration management restores a drifted service by re-converging it rather than repairing it by hand.

4. Demonstration Procedure

The following sequence is executed live. It assumes the DigitalOcean account has been emptied by the systems administrator beforehand.

  • From the workstation terminal, start and enter the control node: multipass start ansible-vm followed by multipass shell ansible-vm.
  • Change to the project directory: cd ~/wordpress-project.
  • Show the DigitalOcean console to confirm no project droplets exist.
  • Run the full build: ansible-playbook site.yml --ask-vault-pass, and supply the vault password. This is the only manual input required.
  • While the playbook runs, narrate the task names as they scroll: SSH key upload, droplet creation, SSH wait, package installation, firewall rules, database creation, Git clone, configuration edit, virtual host.
  • On completion, show the play recap reporting failed=0 for both hosts.
  • Refresh the DigitalOcean console to show both correctly named droplets now active.
  • Browse to both public IP addresses to show WordPress serving from each, completing the installation wizard and logging in to the dashboard to confirm full functionality.

Contingency. If the apt mirror returns 404 errors during the demonstration, the recovery is to add a task pointing the droplets at archive.ubuntu.com in place of the DigitalOcean mirror. Having that snippet prepared in advance converts a failed demonstration into a demonstrated troubleshooting capability.

- name: Use the main Ubuntu archive instead of the DO mirror
  replace:
    path: /etc/apt/sources.list
    regexp: 'mirrors\.digitalocean\.com/ubuntu'
    replace: 'archive.ubuntu.com/ubuntu'
